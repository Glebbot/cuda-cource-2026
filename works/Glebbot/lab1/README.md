# Lab 1: Vector Operations and Activations — Векторные операции и активации

## Описание

Программа на CUDA считает три поэлементные операции над векторами `float`:

- сложение `x + y`;
- SAXPY `alpha * x + y`;
- ReLU `max(0, x)`.

Каждая операция реализована собственным ядром в двух вариантах доступа к памяти: коалесцированном (`--mode coalesced`, по умолчанию) и некоалесцированном (`--mode noncoalesced`). Оба варианта выполняют одинаковую работу над одинаковым числом элементов и дают одинаковый результат; отличается только то, какой поток какой элемент обрабатывает.

После записи результата программа замеряет время H2D, каждого ядра, D2H и полного цикла для выбранного режима и нескольких размеров блока и печатает замеры в stdout.

Эталон для проверки — NumPy: `x + y`, `alpha * x + y` и `np.maximum(0, x)` над массивами `float32` (`tests/check.py`).

## Запуск

```bash
./build/submission --help
./build/submission --input data/example.txt --output coalesced.txt
./build/submission --input data/example.txt --output noncoalesced.txt --mode noncoalesced
```

- `--input` — текстовый файл: `N alpha`, затем `N` пар `x y`. Числа разделены пробельными символами, читаются в FP32.
- `--output` — `N` строк `x+y alpha*x+y max(0,x)` в исходном порядке, 9 значащих цифр, без заголовка.
- `--mode` — `coalesced` (по умолчанию) или `noncoalesced`. Оба режима выполняют все три операции.
- `N = 0` — корректный вход: программа записывает пустой файл и возвращает 0, ядра не запускаются.
- Коды возврата: `0` — успех, `2` — неверные аргументы или вход (нет файла, неверное `N`, не хватает пар, лишние данные, мусор вместо числа, неизвестный режим), `1` — ошибка CUDA или записи результата.
- Замеры времени печатаются в stdout строками `bench block=<B> metric=<h2d|add|saxpy|relu|kernels|d2h|full> median_ms=… min_ms=… max_ms=…`. В `--output` попадает только результат.

## Реализация

Код: `src/kernels.cu` — ядра и их запуск, `src/main.cu` — разбор аргументов, ввод-вывод, работа с памятью и замеры, `include/cuda_check.h` — проверка ошибок CUDA.

**Коалесцированный доступ.** Глобальный индекс потока `idx = blockIdx.x * blockDim.x + threadIdx.x`; поток обрабатывает элементы `idx, idx + stride, idx + 2·stride, …`, где `stride = gridDim.x * blockDim.x` (grid-stride цикл). Сетка — `ceil(N / block)` блоков, то есть на практике один элемент на поток. В каждый момент 32 потока варпа обращаются к 32 соседним `float` — одной 128-байтной линии, и обращение обслуживается минимальным числом транзакций.

**Некоалесцированный доступ.** Поток `tid` обрабатывает непрерывный кусок `[tid · 64, tid · 64 + 64)` (`kChunk = 64`). Сетка — `ceil(ceil(N / 64) / block)` блоков. На каждой итерации соседние потоки варпа обращаются к адресам на расстоянии `64 · 4 = 256` байт, поэтому одно обращение варпа затрагивает 32 разных 32-байтных сектора, из каждого используется 4 байта.

**Границы.** В обоих вариантах индекс сравнивается с `N` (`i < n`, конец куска `min(start + 64, N)`), поэтому `N`, не кратное блоку или 64, обрабатывается корректно; при `N = 0` ядра не запускаются.

**Память и ошибки.** `run_gpu` выделяет 5 буферов (`x`, `y` и три результата) через `cudaMalloc`, копирует `x`, `y` на устройство, запускает три ядра, синхронизируется и копирует результаты обратно, затем освобождает память через `cudaFree`. Каждый вызов CUDA обёрнут в `CUDA_CHECK`; после каждого запуска ядра проверяется `cudaGetLastError()`. При ошибке сообщение пишется в stderr, код возврата — 1.

## Проверка корректности

`tests/check.py` генерирует входы, запускает `build/submission` в обоих режимах и сравнивает результат с NumPy на тех же входах.

- Входы: `x`, `y` равномерно в `[-100, 100]`, `alpha` равномерно в `[-4, 4]`, seed 2026. В начало массива подставляются `0`, `-0`, `1`, `-1`, `1e-30`, `-1e-30` — нули и значения разных знаков.
- Размеры: 1, 2, 31, 32, 33, 255, 256, 257, 1000, 2^20 — меньше блока, около границы блока (256) и не кратные ему.
- Допуски: сложение и ReLU должны совпадать с NumPy точно (FP32, `+0 == -0`). Для SAXPY задание разрешает FMA: GPU округляет `alpha * x + y` один раз, NumPy — дважды. Их разница ограничена величиной операндов, а не результата, поэтому допуск: `|got − ref| ≤ 2 · eps32 · (|alpha · x| + |y|)`, `eps32 = 2^-23 ≈ 1.19e-7`.

| Тест-кейс                                     | Ожидалось                                        | Получилось |
| --------------------------------------------- | ------------------------------------------------ | ---------- |
| Пример из задания, `coalesced`                | код 0, совпадение с `data/example_expected.txt`  | код 0, совпало |
| Пример из задания, `noncoalesced`             | код 0, совпадение с `data/example_expected.txt`  | код 0, совпало |
| `N = 0`, оба режима                           | код 0, пустой файл                               | код 0, пустой файл |
| Случайные, N = 1, 2, оба режима               | add/ReLU точно, SAXPY в допуске                  | add/ReLU точно; SAXPY точно (ошибка 0) |
| Случайные, N = 31, 32, 33, оба режима         | add/ReLU точно, SAXPY в допуске                  | add/ReLU точно; SAXPY макс. ошибка 3.05e-5, ≤ 0.456 допуска |
| Случайные, N = 255, 256, 257, оба режима      | add/ReLU точно, SAXPY в допуске                  | add/ReLU точно; SAXPY макс. ошибка 3.05e-5, ≤ 0.498 допуска |
| Случайные, N = 1000 и 2^20, оба режима        | add/ReLU точно, SAXPY в допуске                  | add/ReLU точно; SAXPY макс. ошибка 3.05e-5, ≤ 0.500 допуска |

Итог: все 24 проверки пройдены. Сложение и ReLU совпадают с NumPy побитово. Максимальная абсолютная ошибка SAXPY — 3.05e-5: это 1 ulp FP32 для значений порядка 256–512 (`|alpha · x|` доходит до 400), то есть ровно разница между FMA на GPU и двумя округлениями в NumPy. Отношение ошибки к допуску не превышает 0.5. Каждый запуск получает свой вход из одного генератора с seed 2026, поэтому ошибки двух режимов при одном N могут различаться.

## Результаты

Методика:

- H2D (`x`, `y`), каждое ядро и D2H (три результата) измеряются событиями CUDA (`cudaEventRecord` / `cudaEventElapsedTime`) — время на GPU. Ядра запускаются асинхронно, поэтому между ними стоят события, а не CPU-таймер.
- Полный цикл H2D → три ядра → D2H измеряется CPU-таймером `std::chrono::steady_clock` до `cudaEventSynchronize` по последнему событию.
- Выделение памяти (`cudaMalloc` пяти буферов) измеряется отдельно и в полный цикл не входит: 0,4 мс при N = 3, 0,6 мс при 2^16, 1,7–2,1 мс при 2^20, 2,9–3,1 мс при 2^24.
- Для каждого размера блока (64, 128, 256, 512, 1024): 3 прогревочных прогона, затем 20 измеряемых. В таблицах — медиана; полные данные с минимумом и максимумом даёт `tests/bench.py`.
- Входы: `x`, `y` равномерно в `[-1, 1]`, `alpha = 1.5`, seed 2026. Память хоста обычная (pageable).

**Полный цикл, блок 256.** «Ядра» — сумма медиан add + SAXPY + ReLU.

## Выводы

**Коалесцированные ядра ограничены пропускной способностью памяти.** На N = 2^24 ядро add достигает ~420 ГБ/с при теоретическом пике RTX 3070 Laptop 448 ГБ/с (256-битная шина GDDR6, 14 Гбит/с) — около 94 %. Это подтверждают соотношения времён: SAXPY ≈ add (лишнее умножение бесплатно, массивов столько же — три), ReLU ≈ ⅔ add (два массива вместо трёх). Вычисления здесь ничего не стоят, время определяется объёмом прочитанных и записанных байт.

**Некоалесцированный доступ в ~13 раз медленнее** (6,2 мс против 0,48 мс, 32 ГБ/с против 420 ГБ/с на 2^24). При шаге 256 байт между соседними потоками каждое обращение варпа требует 32 отдельных сектора по 32 байта, из которых используется по 4 байта — в 8 раз больше трафика на полезный байт плюс в 32 раза больше транзакций. Кэш это не компенсирует: каждый поток возвращается к той же линии на следующей итерации, но одновременно работающих потоков десятки тысяч, их рабочий набор (сотни байт на поток на каждый массив) намного больше L1 и L2 (4 МБ), и линии вытесняются раньше повторного использования.

**Размер блока при коалесцированном доступе почти не влияет:** 64–1024 потока дают 419–423 ГБ/с. Блоков достаточно, чтобы загрузить все 46 SM, и упор — в память, а не в конфигурацию запуска. В некоалесцированном режиме на 2^24 размер блока тоже почти не важен (32–33 ГБ/с).

**Некоалесцированный режим на малых N сравнивать некорректно.** При `kChunk = 64` потоков в 64 раза меньше, чем элементов: на 2^16 их всего 1024, и блок 1024 даёт один блок на один SM из 46 — время растёт с размером блока в 14 раз не из-за доступа к памяти, а из-за простоя GPU. Поэтому режимы сравниваются на 2^24, где блоков от 256 до 4096.

**Передачи CPU↔GPU дороже вычисления почти всегда.** На 2^24 H2D и D2H занимают ~45 мс из 46,6 мс полного цикла (~97 %), ядра — 1,3 мс. Передачи идут со скоростью ~7 ГБ/с (128 МиБ за 18,6 мс, 192 МиБ за 26,6 мс; PCIe и pageable-память), это в ~60 раз медленнее, чем ядро читает видеопамять. Даже некоалесцированные ядра (16,9 мс) дешевле передач. На малых N (N = 3) время ядра ~4 мкс — это накладные расходы запуска, а полный цикл ~0,2 мс — задержки `cudaMemcpy`. Для таких операций с одной-двумя арифметическими операциями на элемент GPU выгоден, только если данные уже на устройстве и дальше обрабатываются там же.

**Ограничения.** Замеры сделаны на ноутбучном GPU под WSL2: передачи имеют заметный разброс (максимумы до 1,5× медианы), pinned-память не использовалась. Время чтения и записи текстовых файлов в замеры не входит.

### Полный запуск

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target submission
./build/submission --input data/example.txt --output coalesced.txt
./build/submission --input data/example.txt --output noncoalesced.txt --mode noncoalesced
```
